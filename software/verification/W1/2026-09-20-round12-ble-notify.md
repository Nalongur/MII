## 本轮完成

- 增加 TX 通知特征 `4d494902-7a91-4c11-9a5e-4d4949563701`，通知 CCCD 写入要求加密链路；服务继续在 Debug/Release 默认关闭。
- `queue_control_payload()` 把一个已编码 Envelope 包成规范帧，只执行零等待静态队列提交，不在调用者上下文执行 NimBLE/NPL 操作。
- 既有协议任务在最长 50 ms 的轮询周期内把工作投递给 NimBLE host；host 上下文独占四帧固定 FIFO 和 MTU 分片状态。
- 通知值严格按 `ATT_MTU - 3` 分片：MTU 23 时最大 20 B，首选 MTU 247 时最大 244 B；完整帧上限 616 B。
- `BLE_HS_ENOMEM`/`BLE_HS_EBUSY` 每 20 ms 重试，第三次失败后丢弃当前整帧，防止永久拥塞；其他发送错误立即丢弃当前帧并继续后续工作。
- 生产者队列和 host FIFO 各固定四帧，均不动态分配。提交队列满立即返回 `ESP_ERR_NO_MEM`。
- 每个生产者项同时携带连接代际与订阅代际。退订/重订、断连/重连、host reset 或句柄复用后，旧项无法复活到新生命周期。
- 退订、断连、连接替换及 host reset 会停止重试、清空生产者队列并冲刷 host FIFO。
- 新增 TX 主机测试、UBSan 运行和 8 项静态约束，总静态基线由 183 项增至 191 项。

## 验证边界

- 没有连接、烧录或启动 MII V7；没有实际广播、配对、MTU 交换、CCCD 写入或通知。
- 主机分片测试不能模拟控制器缓冲、连接间隔、射频丢包、手机后台限制或真实断连时序。
- Secure Connections Just Works 仍只提供加密而不认证对端身份；RX 命令继续隔离，当前 TX API 也不是可信业务响应授权。
- 通知本身没有应用层确认。需要可靠交付的业务仍须在协议层定义响应关联、确认、超时和幂等重试。
- 当前内存计数和队列边界已静态固定，但尚未测量目标板运行时堆余量、NimBLE host 栈水位或功耗。
